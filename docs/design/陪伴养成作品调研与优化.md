# 陪伴养成作品调研与优化

调研日期：2026-11-17。范围：开源项目的状态、事件、记忆和低打扰逻辑，结合天依互动养成包 0.2.1 提出可实施改进。下文区分源码已经存在的能力与建议；建议不代表已经实现。网页为本次查阅的 main/master 或指定发布页，后续内容可能变化。

## 当前项目已经具备的能力

依据 `deskpet/mods/bond/store.py`、`events.py`、`mod.py`、`widget.py` 和包内 README：

- 独立 Mod API 3；SQLite 存档；亲密度每类每日首次 +10、五类共 +50；离线不扣，旧 XP 不覆盖。六阶段阈值为 0 / 40 / 150 / 350 / 700 / 1400。
- 纪念册只记真实互动、阶段、自然完整听歌、演出和主动留言；听歌覆盖与日奖励分别验证。阶段会解锁称呼、舞台、回忆与纪念。
- 主动保存的歌曲喜好和疲惫事实可以查看、删除；聊天上下文只注入已有事实，并禁止编造共同经历。
- 全部 Mod 通知共享宿主的免打扰、额度与冷却；小心愿可设为每日 0～5 次，默认 3 次；无回应不扣数值。
- 研究开始时，小心愿随机选择、统一十五秒结束并展示秒数；阶段只统一限制为“熟悉以后”。这两点是最值得优先优化的部分。

以上是读取时的基线，后续本轮实际修改以主任务的代码、测试和交付说明为准。本文没有把尚未核验的修改归入“已实现”。

## 四个可验证参照

### 1. VPet：数值决定状态，状态决定表现

`GameSave_VPet` 的 `CalMode()` 从健康、心情、好感推导生病、低落、普通和开心；`EatFood()` 将部分补充暂存，`StoreTake()` 逐步释放。它提供了数值、状态和表现分离的明确参照。[VPet 存档与状态计算源码](https://github.com/LorisYounger/VPet/blob/main/VPet-Simulator.Windows.Interface/GameSave_VPet.cs)

对本项目的启发是让关系阶段产生可感知反馈，而不是再加一个等级条：升级后留下可回看的阶段纪念、更新舞台、改变少量日常回应。瞬时饱食、工作、睡眠仍由宿主管理，Mod 不另造一套相互争抢的状态机。

不借鉴健康与饥饿的额外惩罚链。天依目前已经有音符、饱食、心情，再复制 VPet 的完整经济与健康体系会增加照料负担。本次没有找到并验证 VPet 的长期个人记忆实现，不能将其数值存档称为语义记忆。

### 2. Monika After Story：事件有历史和开放条件

MAS 的 `Event` 保存 `shown_count`、`last_seen`、`aff_range`、起止日期和 `show_in_idle`，并区分主动菜单、随机话题与排队事件；这是确定性的事件元数据，并非依赖语言模型即兴生成。[MAS Event 定义源码](https://github.com/Monika-After-Story/MonikaModDev/blob/master/Monika%20After%20Story/game/definitions.rpy)

其亲密度模块有每日增益限制，也有扣除、缺席与道歉机制；当前 `_grant_aff` 包含随机每日阈值，不能把文件开头的旧注释“每日 7 点”当成现行固定规则。[MAS 亲密度源码](https://github.com/Monika-After-Story/MonikaModDev/blob/master/Monika%20After%20Story/game/script-affection.rpy)

对本项目可借鉴的是小心愿“先判断能否出现，再优先未见，最后避开近期重复”，以及阶段变化后开放少量新事件。无需复制复杂事件引擎：已有 `notices` 的种类、日期、状态足够支撑最小版本。

不借鉴亲密度倒扣、离开后的情绪追责、隐藏随机涨幅和反复道歉。这些是特定角色叙事选择，不符合本项目“不惩罚离线”的目标。也不照搬其恋爱脚本或角色素材。

### 3. Shimeji-ee：短动作组成连续行为

`behaviors.xml` 用环境条件、`NextBehavior` 和权重连接短行为。例如追鼠标后转为坐着看鼠标，并以小权重插入其他姿态；拖动、抛出等行为不参与普通随机池。[Shimeji-ee 行为配置](https://github.com/TigerHix/shimeji-ee/blob/master/conf/behaviors.xml)

对本项目的启发是互动有短小自然的后续：摸头后偶尔挥手、点心后满足、演出后谢幕。只使用现成且已适配动作；动作请求被工作、睡眠或拖动挡住就等待或略过，不能抢用户正在做的事。

不借鉴多只复制、移动其他窗口等桌面恶作剧。这个配置也不能证明存在关系成长或长期记忆，本次仅把它作为行为编排参照。自然动作变化不应额外发亲密度，以免形成刷动作收益。

### 4. BongoCat：把“让开”做成明确设置

官方 2.2.0 发布记录列出无操作时隐藏、隐藏延迟和按住修饰键交互等窗口设置；2.3.1 修复鼠标悬停时隐藏的行为，说明低打扰既要有选项，也要覆盖不同交互设置的组合。[BongoCat 2.2.0](https://github.com/ayangweb/BongoCat/releases/tag/v2.2.0)、[官方后续发布记录](https://github.com/ayangweb/BongoCat/releases)

可借鉴其设置以实际效果命名的方式：本包入口可以叫“今天不再提醒”“小心愿频率”“专注时静静陪伴”，把用户能控制的结果写清楚。按键反馈不是关系成长；本次未验证其长期记忆或养成系统，不将其归为亲密度实现案例。

不为本包引入全局按键采集。当前宿主事件已经能说明用户与天依实际做过什么，记录其他软件的按键对养成目标没有必要。

## 建议实施的五项改进

以下为本项目设计判断，不是上述作品已经验证的用户实验结论。

| 优先级 | 改进 | 具体做法与验收 |
| --- | --- | --- |
| P0 | 把小心愿从限时任务改为邀请 | 普通愿望保留约两分钟回应窗口；安静陪伴仍按真实十五秒计时。面板不显示催促式秒数，提供“稍后”“今天不提醒”；过期不惩罚、不补发追问。接受邀约与安静计时分开，不能静默当作同意。 |
| P0 | 先过滤，再轮换事件 | 睡眠/忙碌/小游戏时不发邀约；没有歌单不抽听歌，吃饱不抽投喂。优先本日未出现的种类，近期出现过的降低权重或冷却；熟悉、信赖、默契逐步扩展小事件池。用固定候选列表，勿将字符串条件交给动态执行。 |
| P1 | 今天首页只推荐一件合适的小事 | 顶部保留阶段和亲密进度；依据未完成类别与可用能力推荐一项，旁边说明预计时间。完整五类记录可以展开查看。全完成显示“今天的小事已经记下，想来就来”；避免红色未完成、连续签到和“还欠几项”。 |
| P1 | 阶段解锁变为可回看的反馈 | 阶段卡明确展示本次真正得到的称呼、配色或纪念；忙碌时先保存卡片，空闲再轻提示。用户已打开养成页时尽量在页内呈现，避免叠出弹窗。到顶后仍可积累真实纪念，不额外制造第二套成长条。 |
| P2 | 记忆有来源，并允许停止提醒 | 偏好记录显示用户主动保存的日期和歌曲；回忆引用听歌、留言、演出等来源。分别提供“停止用这条提醒”和“删除这条记录”，删除后不再注入上下文或触发关心。保留现有无后台额外模型调用的做法。 |

最小落地顺序：先做 P0 的期限与轮换，再整理今日首页；后续再增加有素材支撑的阶段事件。五类每日上限与六阶段阈值维持基线，先观察实际使用，避免同时改规则和展示，导致无法判断变化来源。

## 验证边界

需要验证的重点是行为，而非截图是否好看：同一类别一天只奖励一次；忙碌时不发小心愿；稍后与今日静音确实阻止后续提醒；没有歌单或已吃饱不会出现不可完成邀约；过期、关闭程序或离线不扣亲密度；删掉事实后不再引用；旧存档升级保留纪念与偏好。

本次只进行了主来源阅读与本地源码对照，没有对以上四个项目进行安装体验、长期留存实验或完整代码审计。低打扰窗口选项只核验了 BongoCat 官方发布记录，未据此宣称已审计它的实现。没有复制第三方代码、界面资产、角色图或音频；未来若实际复用，须针对具体文件及素材分别核对授权。

## 本轮实际落地

以下是本轮后续读取 `events.py`、`mod.py`、`widget.py` 确认的代码变化，属于源码复核结果；测试执行和实际界面验收以主任务交付记录为准。

- 普通小心愿回应窗口改为 120 秒，安静陪伴仍为 15 秒；摘要改为“方便时回应就好”或“不互动就好”，不再显示秒级催促。晚到的普通互动会先结束过期愿望，不追认该愿望的成功；日常真实互动奖励仍由原规则处理。
- 小心愿按当天已有记录过滤种类，已回应、过期或主动略过的种类当天不再随机出现。没有歌单不抽听歌、饱食与音符不满足不抽投喂的过滤继续保留。
- `defer(today=False)` 将当前邀约记为略过并持久保存 30 分钟暂停；`defer(today=True)` 保存当天暂停，重启后仍生效。它们只控制小心愿，不关闭用户主动聊天、纪念提醒或原有全局通知设置。
- `BondMod.tick()` 在宿主忙碌或活动窗口打开时延后阶段提示，并在有活动小心愿时跳过普通回忆提醒。阶段纪念先前已保存在存档中，未因延后而删除。
- 今日页改为双列互动卡，卡片有原控制、点心、聊天、歌单和演出的直接入口；顶部只显示一条推荐。完成记录保留，文案明确忙碌、离线不扣分，全部完成后提示安心休息。称呼等设置移至设置页，长页支持滚动。

当前推荐覆盖“先摸头”“再聊天”及其余情况下的自由选择，并非完整的、根据所有能力与耗时排序的推荐器。上文 P1 的详细预计时间、阶段页内呈现，以及 P2 的单条停止提醒仍是后续建议。阶段事件池也尚未按熟悉、信赖、默契分别扩展。

### 只读复核结论与测试重点

本次没有发现上述改动中的阻断级新增漏洞。仍需覆盖以下边界：

1. 用可控时钟验证普通心愿在 119 秒内能完成、120 秒及之后不会追认；安静心愿在 15 秒完成，中途互动或宿主进入忙碌会取消。
2. 生成不同种类的邀约，分别回应、过期、略过，再检查当天都不重抽这些种类；可用候选耗尽时停止，而不是报错或突破过滤。每日数值是上限，候选少于上限时不保证发满。
3. 略过后立刻重启，确认 30 分钟内不发小心愿，之后只从剩余种类中选择；当天暂停在重启后继续有效，在正常跨日后解除。测试正常跨日和系统时钟回退时的区别，保持奖励日不倒退的原设计。
4. 暂停只影响小心愿，生日纪念仍可保存，手动聊天照常；确认用户看到的说明没有把它描述为关闭所有通知。
5. 升级时保持工作或活动页打开，不发送阶段通知；关闭活动页且空闲后才尝试通知。全局通知暂时拒绝时，待提示状态应继续保留。
6. 分别触发五类互动，确认卡片状态、单项建议和每日封顶一致；在没有 API、没有歌单、已吃饱的条件下仍能找到离线留言、安静陪伴或吃饱后歇歇入口。

复核时发现一个文案与行为的轻微不符：若“稍后”提示写成“再提这个小心愿”，用户可能以为原邀约会回来；实际同日去重会排除该种类，应该解释为“暂停小心愿提醒 30 分钟”。这不影响存档和亲密度正确性。

另有两项保留行为，不宜误报为已解决：阶段窗口的 `refresh()` 仍可在用户已打开养成页时自动展示阶段对话框；待提示阶段只保存在内存中，进程退出后不会恢复待发通知，但已经生成的阶段纪念仍在存档。这两项均为既有行为，本轮仅延迟宿主忙碌时的主动提示。

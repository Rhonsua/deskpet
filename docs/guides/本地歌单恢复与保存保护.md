# 本地歌单恢复与保存保护

2026-10-30：用户反馈本地已添加的歌曲无法点播。检查时 `library_v1` 已是合法但空的歌单，MP3 文件仍存在；播放历史证明曾播放过相关歌曲。未找到丢失前的完整歌单配置，无法确定原歌单名称、分组顺序，也无法据此确认最初是谁或哪条路径写空。

## 已定位的旧缺陷

旧解析器一条歌单异常（例如 `paths: null`）就会放弃整个歌单集合，回退为空列表。音乐面板定期保存没有区分“新用户空列表”和“解析失败空列表”，可能进一步覆盖原数据。已用隔离数据复现这一机制；它是需要修复的缺陷，但尚不能证明就是此次丢失的最初原因。

## 保存保护

- 在进入旧解析器之前严格检查歌单结构。无效配置尝试恢复独立快照，再尝试备份；都不可用时保留原始配置并阻止自动保存。
- 用户数据目录保存 `music-library.json` 以及一份 `music-library.backup.json`，使用原子替换。清空歌单仍保留上一份非空备份；合法空歌单不会在重启时被擅自恢复。
- 保存前检查共享设置是否已被另一实例改动；发现变化拒绝旧实例覆盖。此检查配合现有单实例锁使用，并非跨进程事务锁。
- 备份写入失败时不写回注册表；写回失败也会显示提示。歌单更改和网易云下载入库使用同一保存入口。
- 所有备份只保存路径，不复制、移动或删除音乐文件。

## 本次恢复方式

从本机 `pet.db` 播放历史找回 65 个仍存在的文件：原 MP3 目录 11 首、网易云下载目录 54 首。按来源建立“本地音乐（恢复）”和“网易云下载（恢复）”，与恢复时已有歌单合并，跳过已有路径，不覆盖 B站歌单。不把同目录中没有播放历史证据的额外文件自动算作原歌单。

恢复前原设置与数据库备份、待恢复清单和执行结果保留在 Git 忽略的 `local-work/music-recovery-20261030/`。原歌单名称和顺序不可恢复；最终是否应用及数量以其中 `recovery-report.json` 为准。

本次已执行恢复并重新启动源码版桌宠：新增 65 首，保留原空歌单及 5 条 B站记录，默认选中“网易云下载（恢复）”。重启并经过自动保存后再次只读核实：65 个路径仍存在，两份快照均有效，搜索“反乌托邦”返回 3 个本地候选。

## 点歌处理

明确的“播放＋歌名”先查实际歌单，避免模型没有搜索就断言不存在。多匹配由 API 在真实候选中选择，无候选不会随机播放其他歌。播放前再次检查候选身份、文件存在性和请求期间的状态变化。

验证：90 项相关测试通过，包括真实 Qt 后台进程连接本机假 HTTP 服务的两阶段选歌。真实 API 使用合成标题验证简称选歌，调整宽松版本识别后通过；该检查未播放用户音乐。既有用户歌曲的实际听感仍由用户试听确认。
